# Runtime Interfaces and Transaction Linking

English | [中文](runtime.zh.md)

This page corresponds to the service, execution and exception handling in the [README](operation_manual.md), and to steps 2–6 of [round_plan](../prompts/round_plan.md). It describes the files and interfaces in the package; it does not represent the robot's current state or a new motion authorization. Operating rules and code capability must be distinguished; known differences are listed at the end of this page.

## Package root and environment

Use only the `g1d_chess/` of this deployment. Entry points and modules are listed in the [script inventory](round_script_inventory.md); the release file list is `manifest.json` in the root directory. Service scripts locate the package root from their own location, and the camera `imageclient.py` is loaded from this package's cameras package; no user-level skills, old project directories or Codex CLI are needed. The serial submitter imports the file/schema functions of `checkpoint_runner.py` and does not start the historical background evaluator in it.

Following the [environment setup guide](environment_setup.md), install the `chess` group of `pyproject.toml` and the external engine, then, following the [first setup](first_game_setup.md), activate the Python environment in which the user has installed the dependencies and call entry points directly with `python scripts/…`. The model is built by `g1_model.py` from the in-package `assets/models/g1/` and does not import `unitree_deploy`; `unitree_sdk2py` and `pyffish` are imported from the target Python environment. Base Python, native libraries, the network and the real hardware are provided by the target environment; the engine is selected via `CHESS_ENGINE`. The network interface, camera server, endpoint and gripper direction are all passed explicitly; configuration templates do not pass arguments to the launcher automatically. The physical left/right wrist mapping is confirmed and filled in on site and cached per process; checkpoints read the camera selection bound to the token.

The transaction `checkpoint_dir` and `image_dir` must be inside this package's `runs/` and use the expanded current absolute path. A token binds the process cache, starting point, scene, executing hand, cameras and gripper direction of the process that prepared it, and is consumed once; do not copy an old token, treat an ordinary prepared file as a complete recovery archive, or restart after prepare and then execute. `restore_cached_transaction` requires a complete trajectory archive with SHA256 and the current compatibility conditions; a single-transaction recovery must not be used as a joint sequence recovery.

Before starting, the launcher cleans up matching old service processes, not limited to the same endpoint; `--status` is kept separate from an actually required start. During execution, while holding a piece, or when the state is unclear, do not recover by restarting. A normal end turns off arm control and keeps the waist hold; the waist hold and arm control are separately managed states. Only when the user explicitly asks to release/end, handle `release_waist` and `shutdown` in order according to the README.

## Ordinary move

`prepare_transaction --request` receives `{"transaction": TX}`, where TX is generated by this package's planner for the corresponding hand and contains `grasp_plan/success_plan/failure_plan/grasp_retry` and all retry, unknown-contact and exit branches. After the full plan preflight passes, enable control, submit `execute_transaction` only once, and keep the long call.

`decision_channel={"mode":"serial","require_worker":false}`. In another tool call, the main session runs `next → 看本次头图+物理执行手腕图 → submit → next` (next → view this checkpoint's head image + physical executing-hand wrist image → submit → next) according to the current stage's prepared file. Planning uses only one head image; the source high/low positions and the target low position after descent are all judged from the head image plus the executing-hand wrist image.

At the source high position, first judge left/right (between the opposing textures of the two fingers) and front/back (in the grippable front section); grippable is enough. At most 3 XY corrections: re-capture after the first two, descend directly after the third; the existing low-position close gate is retained. If XY is insufficient at the low position, use `retry_high` with the gripper open; only when XY is already grippable and only the height causes insufficient textured contact, consider the automatic 5mm `adjust_z`: re-capture after the first, close directly after the second. At most 3 real closes, not reset by replanning. A user's explicit pre-grasp termination uses `submit --failure` to retreat along the cached failure path; a hardware fault may prevent returning home, and ordinary insufficient centering must not be turned into a termination.

After a successful grasp, transport continuously to the target high position, descend to the planned release height, keep holding and capture the head + wrist images. Judge from the expected bottom center, target grid lines/neighboring pieces and drop space in this checkpoint's wrist image; when the target needs correction, move XY directly at the low position keeping the current actual Z/RPY, without rising. At most 3 times: re-capture after the first two, open in place directly after the third, with no extra approval condition. The source high-position and target low-position XY have no per-step/cumulative distance limit, and no motion check is run on the correction segment; the full plan preflight before execution, the visual gates, the counts and handling of actual hardware faults are retained. This is the current operating requirement; see the end of this page for code coverage.

After an ordinary release, retreat vertically to clearance with the gripper open, retreat to staging with the gripper open, close the empty gripper in place, and return to its own init at high position. Between a successful grasp and the target, no fixed staging wait is inserted, and it is not split into a new placement transaction. `placed` only means the action branch completed; it cannot replace the final square acceptance check.

All `open` in a single transaction share `gripper_open_q`; there is no per-waypoint `release_q/gripper_q/no_gate` implementation that can be added at will. During opening/closing the arm holds its actual feedback position, and the open/close waypoint XYZ/RPY does not drive the arm at the same time; if motion is needed, list a separate `hold` move waypoint in the full plan. The tail segment after release approval estimates the open-gripper pose from the latest feedback. The open-gripper q must be prepared for the new device and this round; historical values are not defaults.

A source correction only changes the specified source stage and its offset is not copied to target/init. `actual_relative_offset_xy_m` is relative to the current measured FK, and the submitter converts it to the service reference offset; do not mix it with cumulative reference quantities. The target XYZ/RPY is estimated independently; after an orientation change, re-estimate the tool offset and change orientation at a clear position.

## Continuous capture

The move notation explicitly has two steps: `被吃方 <target> → empty` (captured side `<target>` → empty), then `我方 <source> → <target>` (our side `<source>` → `<target>`). `empty` means moving to the round tray on the same side as the executing hand; it is not an API coordinate. The XY inside the tray is estimated from that round's images; the current release Z convention for both hands is .159m; see the [round tray rules](capture_tray.md).

`prepare_sequence` receives `{"transactions":[REMOVE_TX,MOVE_TX]}`, currently strictly two transactions; it jointly preflights both segments and all their failure/retry branches, and predicts the successful end state of the first segment as the starting point of the second. The first segment does not include a return to init; the first point of the second segment is a vertical hold/rise with `gripper=hold`, then a high-position move to our own source. The same physical hand runs through both segments, and the observing arm keeps this round's pose.

Send `execute_sequence` only once with the joint token. After the first segment's low-position judgment at the round tray, opening in place and verifying that the gripper is fully open, rise vertically and enter the second segment's source gate directly along the preflighted high path; do not return to init, re-enable, open again, or send prepare or other synchronous service requests. The second segment still keeps its own source high/low-position and target low-position judgments, and returns to init only after the whole move is complete. If the first segment fails, is uncertain, or the gripper did not fully open, do not continue blindly.

`recheck_between_transactions=false` means the internal link no longer runs an entry preflight; the normal visual checkpoints and handling of actual hardware/health faults still exist. `collision_checked=false` must not be interpreted as full-tool/neighboring-piece 3D collision having been verified.

`round_tools tokens` generates the two stage prepared files in advance, each handed to the serial tool. After the first stage completes locally, continue with the second stage; do not execute a sub-token separately, and the two sets of identities must not be mixed. Afterwards, take the two real transactions from the sequence result and compute FK offline for each, merge them into the same round's review; the off-board error of the removed piece does not enter the learning accumulation.

## Timeout and exception semantics

The service is a single-threaded synchronous ZMQ REP; during execute/while waiting for a visual decision it cannot handle `get_state/capture/hold/release` from another REQ. During execution, only read local checkpoints and the original long call; a synchronous hold must not be used as an instant emergency stop channel.

| Situation | Meaning of handling |
| --- | --- |
| Client `request_sent=false` | The request was not sent successfully; this does not mean the robot state has been verified. |
| Response timeout or disconnect after `request_sent=true` | The service may still be executing or waiting for a decision; do not blindly resend execute. |
| source serial checkpoint | Interpret by the checkpoint's `deadline_unix_s/wait_indefinitely`; do not treat the configured seconds as an automatic retreat countdown in every case. |
| target release checkpoint | The current `release_alignment.py` sets a finite deadline; look at this checkpoint and do not apply the source indefinite-wait semantics. A timeout does not mean the gripper opens automatically. |
| `next --seconds 45` | Local polling duration, returns as soon as images exist; upper limit 55 seconds, does not change the wait on the robot side. |
| Timeout waiting for the submit accepted receipt | The decision may already have taken effect; first use next to check the local receipt, do not submit again. |
| Explicit pre-grasp failure | Exits along the corresponding preflighted failure path; it is not an emergency stop at an arbitrary trajectory stage. At the low position, first rise vertically with the gripper open. |
| Service SIGINT | With control enabled, requests cancel/hold; with control off, exits; handle only verified processes; it is not equivalent to interrupting the client. |
| release_control / shutdown | The former stops this service's arm publishing, and does not automatically return to init or release the object; the latter refuses while arm control or waist hold is still enabled. |

An exception may keep the piece held and the healthy control hold; do not guess that it has returned home, release automatically, or use SIGKILL in place of a controlled recovery. On-site hardware handling is not provided by the synchronous service.

## Implementation verification boundary

The in-package source code provides left/right hands, joint sequence, two-image camera selection, low-position release judgment and the third-correction pass structure. The actual service capability is checked against the code version it loaded, and the control and fault states follow the current receipts.

"No motion check for XY corrections" is an operating rule of this flow, and **it must not be claimed that the in-package implementation fully satisfies it**: `_release_correction/_checked_release_local` in `release_alignment.py` still call the tool envelope check, local compilation, joint segment check and IK endpoint error check, and the release tail segment also has a return-home bridge check; the source correction implementation must also be checked against `fast_correction.py`. To satisfy this requirement strictly during execution, the corresponding implementation adaptation and validation must be completed first. Nor can the initial full preflight be used to promise that there will be absolutely no hardware or runtime refusal during execution.

Coordinates follow the base/EE definitions of the attached model; the model's zero-locked waist and the actual zero waist hold are two different things and must be verified for real. The EE tool offset is in the in-package model and `motion_harness.py`, and is not equal to an on-site hand-eye result. Head-image board-surface points, piece top surfaces, wrist image pixels and robot arm coordinates are handled separately.

The scope of offline validation is in [validation](validation.md). After completion, perform only the new head-image visual judgment and the offline three-way FK error/JSONL merge review of the two event snapshots; there is no third wrap-up item.
