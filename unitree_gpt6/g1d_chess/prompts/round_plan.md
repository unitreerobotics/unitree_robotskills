# Per-Round Move Execution Prompt

**Grasp-gate termination semantics:** When ordinary centering is insufficient and a re-capture is needed, explicitly submit `retry_high`. When the user asks to terminate this round immediately, or it is confirmed that it cannot safely continue, submit directly at the current pre-grasp checkpoint with `serial_checkpoint.py submit --prepared <prepared.json> --checkpoint <checkpoint.json> --failure`; no visual evaluation file is needed. The service returns to init along the cached failure path and performs no further high re-capture, grasp or release. A low-position `failure` first rises vertically with the gripper kept open, then returns to init continuously. A hardware fault can still abort motion, and you must not claim the arm has returned home; in that case check the live state and do not force the drive.

A brand-new G1D first completes the [first game setup](../docs/first_game_setup.md), then completes the plan below according to the [README](../docs/operation_manual.md) of the current deployment root and this round's user instructions. Use the deployment package root specified by the README for this run; historical games, coordinates and tokens must not be replayed directly. Plan this round's move from the currently measured state and execute only after the full preflight passes; when asked to "plan only", stop at planning.

For the scene, prefer on-site values given by the user that apply. Even if the user provides no on-site information at all, the model estimates all scene fields itself according to Section 5 of the first setup; when some are given, the model fills in the remaining fields. Combining available observations, model data and reasonable assumptions, the model records its basis and uncertainty, then sets and verifies the values directly; supplementary data from the user or extra confirmation is not a precondition, and estimated values are labeled as estimates. Reuse a compatible scene that is already set; after a scene change, re-evaluate and run the full preflight again.

Known differences between the rules and code capability are listed in the [runtime notes](../docs/runtime.md#implementation-verification-boundary); do not treat documented requirements as completed implementation.

In the planning stage, prepare entry points, runtime dependencies and on-demand tools according to the [per-round script inventory](../docs/round_script_inventory.md); the inventory corresponds to steps 1–6 of this prompt, and historical ad-hoc scripts must not be used as general automatic entry points.

**Service and waist hold preparation (consistent with operation manual 0.1.3):** In an environment where the real process is visible, check for a single instance, the working ROOT and the executing-hand entry point; prefer reusing a healthy, idle service with the correct ROOT, and check `ping` and `get_state` serially. Keep the waist at zero as the user has authorized: if `waist_hold_enabled=true`, `waist_zero_verified=true`, `waist_target=[0,0,0]` and there is no fault, record the actual `waist_q` and do not zero again; otherwise, when the service is idle, control of both arms is off, both grippers are closed and empty, and there is no fault, call `lock_waist_zero`, save the receipt and re-read the state to verify. The waist hold must be completed before this round's planning and full preflight; after the waist position changes, refresh the observations and board registration, and old caches become invalid. The waist hold is kept after an ordinary return to init and after arm control is turned off; only when the user explicitly asks to release the waist hold or end the service, follow operation manual 8.1 to confirm arm control is off and the site allows release, then call `release_waist`, and call `shutdown` only if the service must end. If the task only asks to set up the service and the waist hold, wait for commands after verification.

After submitting execute, handle the grasp, release and return-home checkpoints serially according to steps 3–5: `next → 看本次头图和执行手腕图 → 决策 → submit → next` (next → view this checkpoint's head image and executing-hand wrist image → decide → submit → next). Even after the preflight passes, the re-capture and correction gates must still be completed based on this checkpoint's images.

**Prepare the submission package before execution:** Before the robot arm starts moving, determine the absolute paths of this package's Python, `robot_client.py` and `serial_checkpoint.py`, as well as the paths of this round's run, execution request, each stage's prepared receipt, execution result and local evaluation files; independent tool processes do not inherit variables from the previous shell. First complete build and the full preflight, then use `round_tools.py tokens` to generate `tmp/execute_request.json` and `tmp/stage_N_prepared.json`; old files must not be reused. Check that the JSON parses, that token/stage/checkpoint directories match each other, and that the service interfaces used match the current version, and prepare the two evaluation structures in the table below and the `next`/`submit` commands. For an ordinary move, enable control and submit `execute_transaction --request <this-round-execution-request>` **once**; for a capture, submit `execute_sequence` **once**, with the prepared files for both stages ready in advance; the sub-transactions must not be executed separately. execute is a long call: keep its session and handle local checkpoints in another tool call; do not wait for execute to return before viewing images, and do not send other synchronous service requests such as `get_state`, `capture` or `hold` during the long call.

**Visual gate submission content (field names must be complete, booleans use JSON true/false, XY in meters):**

| Checkpoint | Required fields in the local evaluation JSON | Checks before deciding and submitting |
| --- | --- | --- |
| source high position and high position after correction | `decision`, `actual_relative_offset_xy_m`, `reason`, `source_identified`, `descent_alignment_verified`, `evidence` | `success`/`adjust`/`failure`. When passing, both booleans are true and XY=`[0,0]`. When correcting, confirm the source identity, give an explicit non-zero XY relative to the current actual FK, and set `descent_alignment_verified=false`. XY has no per-step or cumulative distance limit, and no motion check is run on the correction segment; the correction count and visual gate requirements are retained. |
| pre-grasp low position `preclose` | Same six fields as above | `success`/`adjust_z`/`retry_high`/`failure`. No XY correction may be submitted at the low position. `adjust_z` only requests the preflighted automatic 5 mm lowering; `retry_high` keeps the gripper open and returns to the high position with XY=`[0,0]`; when passing to close the gripper, both booleans are true and XY=`[0,0]`. |
| pre-release low position `pre_release` | `decision`, `actual_relative_offset_xy_m`, `reason`, `target_identified`, `release_alignment_verified`, `obvious_large_offset`, `evidence` | `success`/`adjust`/`failure`. Passing requires the target identified, the landing point safe to release, `release_alignment_verified=true`, `obvious_large_offset=false` and XY=`[0,0]`. Correcting requires the target identified, `obvious_large_offset=true`, and an explicit non-zero XY relative to the current low-position actual FK. No per-step or cumulative distance limit, and no motion check on the correction segment. |

Each `reason` states the source identity or target landing point supported by this checkpoint's images, the left/right, front/back or intersection offset, and why it can descend/close/release or must be corrected. `evidence` contains the paths of the head image and physical executing-hand wrist image returned by this checkpoint; it must not be empty, reuse the template example, or reuse an old checkpoint. `failure`, `retry_high`, `adjust_z` and other non-XY-correction decisions all use `[0,0]`; do not arbitrarily add fields outside the schema or choose your own `grasp_z_m`. Before submitting, check against the current `stage` and `corrections_remaining`. Neither source high-position nor target low-position XY corrections have a per-step or cumulative distance limit, and no motion check is run on the correction segment, including extra preflight, IK reachability, path, surface clearance, joint limit and sampling checks; the full plan preflight before execution, the visual gates, the count limits and handling of actual hardware faults are still retained. This is a documented operating policy and must not be used to claim that the running service implements it. `serial_checkpoint.py submit` automatically binds identities such as token, worker and stage from the current checkpoint; do not fill these fields by hand in the evaluation JSON. Once the images arrive, only make the visual judgment and fill in the prepared structure. First activate the Python environment in which the user has installed the dependencies, set `CHESS_PYTHON` to the absolute path of that interpreter (for example `CHESS_PYTHON="$(command -v python)"`), set `CHESS_SERIAL` to the absolute path of that script in this deployment package root, and set `CHESS_PREPARED` to the absolute path of the current stage's prepared file; set them again in every independent tool call:

```bash
"$CHESS_PYTHON" "$CHESS_SERIAL" next --prepared "$CHESS_PREPARED" --seconds 45
```

After viewing this checkpoint's two images and filling in the evaluation JSON, set `CHESS_CHECKPOINT` to the `checkpoint_path` returned by this `next`, point `CHESS_EVALUATION` to that evaluation file, then submit:

```bash
"$CHESS_PYTHON" "$CHESS_SERIAL" submit --prepared "$CHESS_PREPARED" \
  --checkpoint "$CHESS_CHECKPOINT" --evaluation "$CHESS_EVALUATION"
```

Confirm `accepted=true` before `next`; if a submit times out, first use `next` to check the receipt and do not submit again. The source high/low positions and target low position are gates that normally wait for a visual judgment. After a successful grasp, transport, the link between the two capture segments, the rise after opening the gripper and the return to init are executed continuously by the submitted transaction; do not insert code searches, ad-hoc script patches, extra service requests or manual waits. Handle hardware/control faults with the existing protections; do not force motion for the sake of continuity.

**Open/close waypoints:** During opening/closing the executing arm holds its current measured position; the XYZ/RPY in the waypoint does not drive the arm at the same time. If the arm must move first, list a separate `hold` move waypoint in the plan and open/close after it arrives; it goes through the original full preflight together with the other branches, and no extra preflight path is added during execution. The open-gripper tail segment after release approval estimates the open-gripper pose from the latest feedback.

When planning, follow the [board_position notes](../board_position/README.md) and the [new-model marking task](../board_position/prompts/mark_board.md) to build and visually re-check the 90 points from the current left_high, and check the source/target square names (a–i left → right, 0–9 near → far). The directory does not include real historical coordinates or images. When the board or camera position changes, re-localize; old pixels or old piece occupancy must not be reused, and board-surface intersections must not be taken as piece top surfaces or robot arm XY. Data and re-checks are prepared before execute; after it, they only assist square and offset verification within the visual judgment of item 6.

In the planning stage, use `scripts/mark_board.py init/build/query` with the current original image and the actually visible intersections to generate this round's annotated PNG, the 90-point pixel JSON and CSV; keep fit points and held-out points separate, and even after the numbers pass, the lines must still be verified visually. At the release checkpoint, only read the head-image marks prepared in advance to help identify the target square and neighboring pieces; the landing point is still judged from the grid lines, the expected piece bottom center and neighbor spacing in this checkpoint's executing-hand wrist image. The head image and wrist image are not the same projection; do not convert head-image pixel offsets directly into low-position base XY. After the camera position, waist or board changes, re-mark in the next round's planning stage; do not run registration or look up data while waiting at a gate.

**During plan execution, do not perform any unrelated steps. At a checkpoint that needs a re-capture, re-capture on arrival; once the images are ready, judge, submit and continue immediately: `next → 看本次两图 → 决策 → submit → next` (next → view this checkpoint's two images → decide → submit → next). In particular, a high-position re-capture correction must predict XY directly from the two freshly captured images, without looking up historical data or other information while waiting at the gate. Do not let the robot arm hold a piece while waiting for data lookup, code reading/modification, tests, extra model calls, long explanations, report writing or FK review. All required scripts, templates and parameters are fully prepared before execute.**

`board_position` only outputs board-surface pixel geometry and provides no per-hand source/target end-effector XY prior. Both are still estimated independently from the current images, the executing hand and the actual pose; do not add historical deltaXYZ means, other poses or source corrections directly onto the target.

The intersection criteria of item 4 apply to placing pieces on the board. In the capture removal stage, the round tray on the same side as the executing hand is the target: the physical left hand uses the left tray, the right hand the right tray. Estimate a usable XY inside the tray from this round's images; the release Z for both hands is fixed at 0.159m. Release once the piece is expected to land entirely inside the tray, clear of the tray rim and pieces already placed; aiming at the tray center is not required, and the board intersection criteria do not apply. Fill `capture.offboard_target` with `kind=round_tray` and a `physical_side` matching the executing hand, with tray `z_m=0.159`; the full rules are in the [round tray capture rules](../docs/capture_tray.md). The detailed decision table is in [release landing point judgment](../docs/release_alignment.md).

1. **Starting point and piece selection:** Each round, read the measured poses of both arms and compute the 3D distance from each end-effector XYZ to its own init; if ≤0.10m (10cm inclusive), do not re-init, and only an arm beyond that range needs initialization. Plan directly from the current measured joints and XYZ/RPY of the selected executing arm; the non-executing arm keeps this round's current pose. Neither hand uses a camera pose; the full preflight and the return-to-init tail segment after the move are still retained. Capture only one new `cam_left_high` to plan the move, and confirm the game state together with the current status. First read this game's `move_forecast.json` and match Black's actual reply and the expected position: only if they agree and a next Red move remains is it used as a candidate; if there is no forecast, it disagrees, or it is used up, search the full set of legal moves and save new Red and Black moves for the next 5 rounds. Saving the forecast and confirming progress are done only in the planning stage. Prefer selecting the hand by source: columns a–d left hand, columns e–i right hand (e goes to the right). **Crossing the whole board is allowed, including the right hand to a–b and the left hand to h–i. First run the full reachability preflight for the original executing hand; if unreachable, use the other hand with a full preflight from this round's measured starting point and independently estimated grasp/release poses. Abandon the move only if neither hand can reach it, and search the next legal candidate.** A capture must preflight the whole joint sequence; a single-point IK success does not mean the whole move is executable. `scripts/move_constraints.py` only lists rule-legal candidates and no longer filters by crossing span; see `docs/move_constraints.md`.
2. **Full planning and preflight:** Read [neighbor clearance and accurate placement](../docs/neighbor_clearance_and_landing.md) before planning. After selecting the candidate hand and before estimating, run `scripts/xy_error_history.py show --run <this-round-run> --hand <left-or-right> --context-id <current-compatible-config> --previous-journal <previous-round-run>/docs/execution_xy_errors.jsonl` to read that hand's historical cumulative ΔXYZ mean; when switching hands, read the other hand again, and do not share errors or coordinates. **The source and target XYZ/RPY are each estimated independently from this round's images; the historical mean is only an aid and is not added or subtracted directly.** For source and target on both the Red and Black halves, first try a gripper orientation biased toward lateral; a feasible lateral grasp does not require a lateral release. Only if a stage is unreachable in that orientation, or there is a clear risk of pushing or pinching a neighboring piece that cannot be removed among the lateral candidates, change that stage to a longitudinal bias; after changing the release RPY, re-estimate the target EE XYZ for the new orientation. Check the relation of the whole gripper to neighboring pieces during descent, closing, opening and rising, and reduce obvious interference; perfect zero proximity is not required, and collision is not judged from 2D projection overlap or occlusion. Orientation changes are done at a clear high position, and old EE XY from a different RPY is not reused. After every hand or orientation change, rebuild and run the full preflight of the grasp, retries, orientation change while holding the piece, transport, release, rise, return to init and failure branches; only candidates whose preflight succeeds may be executed. Fill in the spec's error context, reference notes, previous-round journal and this game's round and move; a capture is jointly planned in advance as one sequence. After passing, submit execute only once.
3. **Grasp:** At the source high and low positions, judge only from this checkpoint's head `cam_left_high` and physical executing-hand wrist images; read them according to the camera policy and do not guess the physical hand from the stream name. At the high position, look in two directions: left/right so that the piece is between the opposing textured contact faces of the two gripper fingers, and front/back so that the piece is within the textured grippable section at the front of the fingers and has not slipped behind the gripper. If either direction is not yet enough to grip the piece, estimate the combined left/right and front/back offset from the current two images, give an explicit XY vector aimed at centering in one correction, and re-capture immediately; do not make tentative moves one direction at a time, and pixel-level centering is not required. A single source high-position XY has no distance limit. After the re-capture, if both directions are enough for the textured faces to grip the piece's side walls, and the descent sweep has no obvious risk of pushing or pinching a neighboring piece, descend immediately; only if still not satisfied use the remaining corrections. Source high-position XY corrections are at most 3: re-capture immediately after the first two corrections; after the third correction, pass directly to descend and grasp, with no further high re-capture or visual approval, and do not take the failure retreat because of ordinary insufficient centering. The existing low-position close gate after descent is still retained. Occlusion or close projection by itself is not a reason to refuse the grasp; if the RPY must change, handle it at the high position, and do not rotate the wrist at the low position.

   After descending, check in the new low-position images the left/right and front/back centering, the actual overlap of the piece's side walls with the textured gripping faces of the two fingers, and whether the gripper presses on the top, pushes, or touches neighboring pieces. The close-pass criterion for a stable grasp is: the target piece is between the two fingers, both side walls enter the opposing textured effective gripping faces, the fingertips can wrap the side walls rather than press on the top, and the piece has not been pushed and no neighboring piece is pinched; merely lying within the projection of the open gripper is not enough to pass. If more than half of the piece lies outside the gripper's textured contact area, while XY is already grippable and only the height causes insufficient effective contact area, consider `adjust_z` for an automatic vertical lowering of 5 mm to increase the grasp area; re-capture immediately after one lowering, and only if the effective contact on both sides is still limited only by height and the preflight allows a second lowering, lower again per the existing flow and close directly, with no third low-position gate added. If a left/right or front/back offset keeps the side walls from entering both effective gripping faces, especially when the piece is clearly toward the back of the gripper, lowering Z must not replace correction; keep the gripper open and return vertically to the high position for a re-capture with `decision=retry_high`, XY=[0,0]. A real close that grasps nothing likewise returns to the high position for a re-capture, not a direct failure return to init; at most 3 real closes, accumulated across replans and not reset. A high-position correction may only give an explicit XY relative to the measured FK based on the current two images, without looking up historical images or data; the full plan preflight and the existing clearance protections of the ordinary execution path are retained; the source high-position/target low-position XY correction segments are not motion-checked, and actual hardware or control faults are still handled by the original flow. On a successful grasp, record the raw snapshot asynchronously and transport immediately, without computing FK error.
4. **After descent and before opening, re-capture and decide immediately:** After transporting to the target high position, descend as planned to the release height (on the board, Z=.139m for both hands; when moving a captured piece into the round tray, Z=.159m for both), keep holding, and capture new head and executing-hand wrist images. For placement on the board, rely mainly on this checkpoint's wrist image, with the head image assisting to check the square name: first identify the visible pieces around the target and their intersections, then extend, intersect or interpolate along the two sets of board lines and neighboring intersections in the image to locate a target intersection that may be hidden by the gripper or piece; then use the visible piece outline to estimate the center of the held piece and the expected bottom center after opening, taking into account grip eccentricity and top-surface/board-surface parallax, and compare its left/right and front/back bias relative to the target intersection and its spacing to neighboring pieces. The gripper housing, shadows, a single grid line or a piece edge must not substitute for the landing point, and a small FK error alone is not grounds to pass. Only when the expected center is close to the target intersection, the whole piece can drop cleanly without overlapping neighboring pieces, and opening and rising have no obvious interference, submit `success`, `obvious_large_offset=false` and open in place; a small center offset does not need repeated adjustment. Only when the edge merely covers the intersection, the expected center is clearly off, or it falls between adjacent intersections or in the middle of a square, submit `adjust`, `obvious_large_offset=true`; when the target intersection is hidden, still infer it from visible grid lines and neighboring pieces, do not correct because of occlusion alone, and do not set uncalibrated millimeter/pixel thresholds. reason/evidence record the wrist image path, the visible grid lines/pieces used for localization, the bias of the expected center relative to the intersection, and the nearest neighbor relation. XY is relative to the current low-position actual FK; adjust directly at the low position keeping the current Z/RPY, without rising. This correction segment is exempt from the low-position lateral move prohibition, has no per-step or cumulative distance limit, and is not motion-checked; the visual judgment, count limits and handling of actual hardware faults are retained. The target has its own maximum of 3: re-capture at the release height immediately after the first two; after the third correction, pass directly to open in place, with no further re-capture, visual approval or "sufficient safety basis already exists" precondition for passing. Actual hardware or control faults are still handled by the original flow. When the expected landing point truly cannot be judged or there is a collision risk, submit `adjust`, `obvious_large_offset=true`, `release_alignment_verified=false`, and describe the uncertainty or risk; the target must still be identified and a well-founded explicit non-zero XY given, then the correction is executed directly without a motion check on the correction segment; identification or displacement must not be fabricated. On passing, record the second raw snapshot and freeze the return-home tail segment.
5. **Continuous return home and capture linking:** Ordinary placement: descend → judge from the two low-position images / direct XY fine adjustment if needed → open in place → rise vertically to clearance with the gripper open → retreat to staging with the gripper open → close in place → return to its own init at high position. In the capture removal stage, after confirming the captured piece can be released inside the round tray, open in place and verify through existing feedback that the gripper is fully open, then immediately rise vertically and go along the preflighted high path directly to our own source high position for a re-capture; staging is not a separate wait point, and the second segment does not open again, re-enable, return to init or send other service requests. Return to init only after the whole move is complete; if the gripper did not fully open or hardware/motion protection refuses, stop the link and verify the state. During execution, only handle local checkpoints and the result of the original long call; on timeout, first check the local receipt, and do not repeat execute or a decision submission.
6. **After completion do only two things:** ① Capture one new `left_high`, judge whether the move succeeded and the position offset, and prepare `tmp/visual_review.json`; ② Offline, compute three errors of the actual FK at the two moments "grasp success" and "low-position approval to open and release after descent" — relative to the original plan, the final effective target and the commanded FK at that moment — then use `scripts/xy_error_history.py finish` to carry over into this round's `<this-round-run>/docs/execution_xy_errors.jsonl` all historical lines of the `previous_journal` in the plan summary, and append one line for this round (full errors and the source/target `count`, `sum_delta_xyz_mm`, `mean_delta_xyz_mm` accumulated separately for the left and right hands), while merging with the image judgment and saving to this round's `docs/{第几轮}_{这一轮的走棋子方案}_{时间戳}.json` (round number, this round's move plan, timestamp). The journal is in the same directory as this round's final review JSON; old journals are unchanged, and the new journal is used by the next round to continue accumulating. The accumulation uses only the full ΔXYZ of actual minus the final effective target; samples with visual success, a current event, all three components finite and a 3D magnitude ≤25mm may be learned; old high-position, failed, missing and capture off-board removal samples are kept only as evidence and not counted; the same token is not learned twice. JSONL maintenance belongs to item ②, and the execution gates do not read or write it. Name it like `第N轮_中文着法_YYYYMMDD_HHMMSS.json` (round N, Chinese move notation, timestamp): the round is our N-th move in this game (a new game starts at 1; retries/capture sub-transactions do not increment), the plan is the final Chinese notation of the move, and the timestamp is Beijing time `YYYYMMDD_HHMMSS` at the time of the merged save; a file of the same name must not be overwritten. Prepare the game/round/move/context during planning; when merging, create `docs/` and record `round_number`, `move_plan`, `review_created_at`. The detailed rules are in Section 8 of the operation manual and `docs/xy_error_learning.md`; `pose_review.json` is only intermediate detail. Mark missing data truthfully. The task ends once the final JSON and journal are saved; reply only with the success/offset conclusion, a brief FK error summary and the file paths, and do no further wrap-up work.
