# R1-D chess control (manual agent workflow)

English | [中文](SKILL.zh.md)

The directory of this skill is the package root. Run all commands under the package root with `bash r1d <subcommand>` (equivalent to `python scripts/<entry>.py`; the interpreter is taken, in order, from `R1D_CHESS_PYTHON`, `<package root>/.venv/bin/python`, and the `python3` on PATH). Scripts, configuration, templates, and models are all located relative to the package root; run artifacts go only under `runs/`. Send the gate commands during execution one at a time, each on its own, with absolute paths.

The agent does all of the following: reading the board from images, choosing and sequencing the move, choosing the arm and the poses, and judging every gate. The Python service handles preflight, tokens, motion execution, and safe stop.

There are two layers of processes: the **robot runtime** (called Runtime below; its code is in [third_party/robot_runtime](third_party/robot_runtime/README.md), and it runs as the systemd user unit `r1d-runtime.service`) is the only process that sends commands to the robot; the **chess service** (`bash r1d serve`) calls it through local IPC, and the agent talks only to the chess service. This package has no master script that completes a round automatically.

## Choosing the task and reading the material

- **New environment, new robot, or unconfirmed site**: first read the [README](README.md) and [setup/README](setup/README.md), then run `python scripts/check_environment.py` and `python scripts/setup_status.py` (both offline, no robot connection). The files shipped in `config/` are the calibration results of the reference robot; **setup must be completed before playing chess**: local environment ([step 0](setup/README.md)), [camera check](setup/camera-check/README.md), [arm accuracy calibration](setup/arm-calibration/README.md) and [tracking verification](setup/joint-tracking/README.md), [head camera calibration](setup/head-camera-calibration/README.md), and [chess scene parameters and board calibration](setup/chess-scene-parameters/README.md). Every setup step that moves the robot requires the user's explicit authorisation.
- **Only starting the service, taking over, or checking state**: read "Starting a chess task" in the [operation manual](docs/operation_manual.md), and use `goinit`, `serve`, `handover`, and `client get_state`. After completing the specified scope, wait; do not move pieces automatically.
- **Reading the board, checking the board position, recalibrating after the board moves**: read [board_position](board_position/README.md), and use `boardview`, `fencheck`, `boardpoints`, and `boardcal`. The first board calibration is done in the scene parameters part of setup.
- **Executing one round**: first read [round_plan](prompts/round_plan.md), then follow the workflow below; look up exact commands and fields in the [operation manual](docs/operation_manual.md) and the [script inventory](docs/round_script_inventory.md), and have them ready before motion.
- **Fault, interruption, or the user asks to return to position**: read "Errors, returning to position and ending" in the operation manual, and first verify the actual session and result. An interrupted execute client does not mean the robot has cancelled; do not blindly resend execute, restart the service, or reuse an old token.

The task scope is defined by the current user instruction. Reading documents, tidying directories, or offline checks do not authorise starting the service or motion.

**Check before motion**: before enabling motion for the first time (`serve --allow-motion`, `enable_control`, `goinit --execute`, `start --execute`), run `python scripts/setup_status.py --require`. Do not move pieces while any required item is still "reference value, not set up": tell the user which items are missing and complete them following the setup procedure; only when the user explicitly decides to keep a reference value for an item, record it with `--confirm <item> --note "<basis>"` and then continue.

## Single-round workflow

1. **Take over**. After a robot restart, first run `bash r1d goinit` to preview, and run `goinit --execute` only after the user confirms it is safe (it does no preflight; do not execute it on your own). Then start the Runtime (`systemctl --user start r1d-runtime.service`; this unit is generated by `python scripts/install_runtime_service.py --write` before first use) and the service (`bash r1d serve --allow-motion --arm <arm>`), and take over with `handover --arm X --execute` (when a hold unit exists) or `client enable_control --arm X`. After `get_state` confirms no fault, `head_waist_session_active=true`, and head pitch about 0.62, run `client release_control` to disable execution and keep the session. After the previous round returns to init, the service has unloaded the arms and ended the session, so you must take over again every round.
2. **Create the run and check both arms**. `round init --run <package root>/runs/<this-round>`. If the TCP of each arm is ≤10 cm from its own init, start directly from the current position; otherwise first run `client prepare_init`/`execute_init`.
3. **Read the board**. Take only one `cam_left_high` planning image, confirm the complete position and the opponent's actual move, and write `board.json`. When it is unclear, use `boardview` and `fencheck` (only for reading the board, not for estimating poses).
4. **Choose the move**. If there is a prediction from the previous round, first run `engine match`; on a mismatch or when the prediction is exhausted, run `engine analyze`.
5. **Choose the arm and the poses**. Prefer the left arm when the source is in files a–d and the right arm when it is in files e–i; switch arms with `client set_active_arm` and retake the image. Generate TCP poses (not piece positions) with `bash r1d pose pose --role source|target|tray ...` and fill in `round_spec.json`. For a capture, first put the opponent's piece into the tray on the same side.
6. **Build the plan, preflight, get tokens**. `round build` → `client prepare_transaction` (for a capture use `prepare_sequence`, which preflights the two segments jointly) → `round tokens`. Switch to the other arm only when the whole path is unreachable for the preferred arm, and change the move only when neither arm works. Preflight again whenever the plan, the start point, or the acting arm changes, or the service restarts.
7. **Execute**. After preflight, first run `get_state` and wait about 3 s, then run `client enable_control`, and then submit `execute_transaction`/`execute_sequence` only once (a long call; send no other request before it returns).
8. **Gates**. In a separate call, loop `serial next` → look at this checkpoint's head image and the acting arm's wrist image → `bash r1d gate --decision ...` → immediately `next`. The agent judges each gate itself and submits immediately:
   - Source high gate: `success` if the piece is midway between the two jaws, otherwise `adjust` (XY offset, at most three times).
   - Pre-close gate: `success` if the piece centre has passed the jaw tips and is roughly between the two jaws; use `adjust_pitch` if most of the piece is beyond the jaw tips (at most two times); use `retry_high` only if the piece is so clearly off that a single jaw would push it away.
   - Pre-release gate: measure the landing point independently with the wrist image, do not rely on FK alone; when the deviation is >5 mm submit `adjust` (at most three times), and the last correction must confirm that the piece can be released safely after the correction, otherwise submit `failure` and stop while holding the piece.
9. **Release and return** are completed automatically by the service, which unloads the arms automatically after the return to init.
10. **The review does only two things**: judge success or misplacement from a new head image; record the FK error with `review` plus `history finish`.

On errors or when a return to position is needed, use `bash r1d retract`; it does not replace gate approval. Do not open the gripper manually with `client set_gripper`.

## Actual capability limits

- The `config/` shipped with the package holds the reference robot's results and does not represent the current robot; no geometry or tracking accuracy can be trusted while setup is incomplete.
- The geometry is a model estimate; it can be used for planning and execution, but that does not mean the pick and place is accurate. Neither `placed`, nor a small FK error, nor an accepted command can replace confirmation by the head image after the move.
- Preflight checks only IK, joint limits, the table, and the tool envelope, and only for the acting arm; there is no collision detection for the whole arm, between the two arms, against neighbouring pieces, or against a dynamic environment, so neighbouring pieces must be rechecked against this round's images.
- Adjustments during execution (XY correction, pitch reduction, return to the high position, release correction) are not preflighted; only IK is solved and the result is sent directly.
- There is no automatic piece recognition; `boardview` only helps with reading the image.
- On one host, the same service endpoint can have only one chess service instance.

Report the actions actually completed, the final visual conclusion, the available errors, and the paths of this round's artifacts; when images or results are missing, state the gap and do not fabricate a successful move.
